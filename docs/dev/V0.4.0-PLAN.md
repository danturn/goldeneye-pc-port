### Post-1.0, researched and tracked (do not start in v0.4.0)

Both were investigated 2026-09-22 against the Perfect Dark PC port fork
`perfect-dark-dabs-mod-dabs-mod` (**MIT**, Ryan Dwyer — same license as this
tree; `AGENTS.md` already names the PD port a standing reference, so code may be
adapted with attribution). Fuller sequencing notes live in the local
`docs/dev/notes/MODERN-PORT-FEATURES-BACKLOG.md` §5/§6, which is gitignored — the
durable record is `docs/dev/findings.md` and the summary here.

**Mod support (ROM patches) — viable, medium–large.** Findings **D325–D328**.
- Community mods *repack* the ROM, so vanilla offsets are useless: Goldfinger 64
  (12→24 MB, 797/803 slices differ) and even the content-neutral Random Eye
  randomizer (identical ROM size, yet 803/803 slices differ — content shifted
  +7392). Both die in `tools_pc/d43_emit.py:273` on a vanilla-offset zlib slice.
- **The fix is not a loader rewrite.** PD's `port/src/modimport.c` states our own
  constraint verbatim and instead diffs the patched ROM against stock, extracting
  what differs into a **mod directory** its loader already reads. The game keeps
  running its stock ROM at fixed compiled offsets.
- GE's file table is in the ROM after all (D327 said otherwise; corrected by
  D328): 1172-compressed data segment at ROM `0x21990` — one raw inflate, which
  `port/src/rzdecomp.c` already wraps — table at `0x252c4`, 727 records of 12
  bytes, pointers `0x80020d90`-based, size by differencing adjacent addresses,
  exactly `obInit` (`src/game/ob.c:126`). Verified: **681 exact offset+size
  matches vs `filelist.u.csv`, 0 mismatches**; discovery needs **no hardcoded
  offsets** and reads Random Eye's own table to **704/726 files byte-identical**.
- Remaining work: extraction in C (proven), patch decoding (PD's `rompatch.c` is
  an MIT VCDIFF/BPS/IPS decoder — **removes the GPLv2 xdelta3 constraint**),
  converters taking the extracted table, and the real effort: a
  **mod-directory override layer** — `port/src/romdata.c` reads the ROM only and
  has no analogue of PD's `romfile.moddir` file slots.
- **Hard limit:** mods that *add levels* need new stage-table entries in
  `src/game` — rule 2, not the ABI/layout exception. Either a sign-off or scope
  down to the existing 20 slots. ASM/code mods stay impossible (ROM code is never
  executed here).

**HD texture packs — medium, well-scaffolded. Answers issue #100** ("High
Resolution Textures", open, `enhancement` — a user asking whether HD textures can
be used with the port). Architecture studied from PD's
`port/include/texpack.h` + `port/fast3d/gfx_pc.cpp`; no finding written yet, so
this entry and backlog §6 are the record.
- **Identity is the whole problem, not decoding.** The renderer only ever sees
  the pointer `gDPSetTextureImage` was handed, so PD keeps an address →
  texture-number registry populated where `texLoad()` runs and invalidates it
  when the pool drops (a stale entry names the *wrong* texture). Then three-tier
  matching: texture number → texel checksum (for textures embedded in model
  files) → per-record. Packs are `textures/<texnum>.png`; decode happens on a
  worker so loading does not hitch; the hook is inside `import_texture`, gated so
  it costs one lookup when off.
- Most scaffolding exists here: our `gfx_pc.cpp` is the same lineage
  (`gfx_texture_cache`, `:92,579`), `g_Textures[].texturenum` exists
  (`src/game/chr.c:3894`), and **`GE_TEXDUMP` already dumps textures**
  (`port/fast3d/gfx_pc.cpp:1205`) — it just names them by sequence
  (`r000_f3_s1_64x64.bin`) rather than texture number, so dumps cannot round-trip.
  Renaming that is the single change turning the probe into a pack dumper. A PNG
  decoder is the one new dependency, and zlib is already required.
- Step 1 (the identity registry) is the only novel design decision, and it
  records identity where textures load — a `src/game` touch needing `#ifdef PORT`
  plus a §F note. Settle that at design time, not mid-implementation.
